# 현재 클라이언트 범위

## 로컬 책임

클라이언트는 Windows PC에서 `python -m app`으로 실행됩니다. 로컬 FastAPI 서버가 React UI를 제공하고, 시스템 트레이에서 UI 열기·로그 열기·종료를 제어합니다. 로그는 장애 조사용 `client.log`에 계속 보존하는 동시에 `logging.Handler`의 메모리 링 버퍼와 알림 큐를 통해 별도 GUI에 전달합니다. Tkinter 인터프리터와 창 이벤트 루프는 메인 스레드에서 실행하고 트레이는 분리 실행하여 종료 시 Tcl 객체도 생성한 스레드에서 정리합니다. GUI는 로그 파일을 반복해서 읽지 않으며, 창을 닫으면 숨김 상태로 전환되어 트레이와 로컬 서버 및 파일 로깅은 계속 실행됩니다. 다시 열면 메모리에 남은 최근 로그를 즉시 표시합니다. 웹 파비콘, 트레이, 로그 창과 클라이언트 종료 확인 창은 검은색 둥근 정사각형 안에 주황색 재생 기호가 있는 같은 아이콘 및 라이트 테마를 사용합니다. 숨겨진 Tk 루트 창은 생성 직후 `withdraw`하여 시작할 때 작업표시줄에 순간적으로 나타나지 않도록 합니다. 종료 확인 창도 숨긴 상태에서 크기와 중앙 좌표를 계산한 뒤 표시합니다. 스크롤바는 내용이 영역을 넘을 때만 표시합니다. 일반 브라우저 탭으로 연 웹 UI는 브라우저 보안 정책과 다른 탭 보호를 위해 트레이 종료 시 강제로 닫지 않습니다.

## 지원 영상 범위

입력으로 지원하는 대상은 길이가 **10분 이상 6시간 미만**인 일반 업로드 YouTube 영상과 라이브 종료 후 다시보기(VOD) 영상입니다. 현재 라이브 스트리밍 중인 영상은 지원하지 않습니다.

영상 관련 작업은 모두 로컬에서 처리합니다. `/bin`의 `yt-dlp.exe`, `ffmpeg.exe`, `ffprobe.exe`를 사용해 영상과 메타데이터를 수집하고, 자막과 분석 보조 데이터를 만들며, 선택 구간을 렌더링합니다.

### 단계별 수집 재사용

파일은 내용이 결정되는 단위에 따라 구분합니다. 영상에서 받은 원본은 `yt-data/{video_id}`, 고정된 처리 결과로서 같은 영상에서 항상 동일한 자료는 `yt-edit/{video_id}`, 작업 수행마다 달라질 수 있는 자료는 `yt-edit/{job_id}`에 저장합니다.

편집 작업 ID는 사용자가 1단계에서 2단계로 넘어가 추가 자료 다운로드를 시작할 때 한 번 확정합니다. 이후 같은 작업 안에서는 추가 자료를 다시 받거나 Whisper 전사를 반복 수행하더라도 새 ID를 만들지 않으며, 분석과 렌더링이 끝날 때까지 같은 ID를 사용합니다.

`yt-data/{video_id}`에는 yt-dlp가 받은 영상 단위 자료를 둡니다. 메타데이터 JSON, 원본 영상, 전체 댓글 JSON, 전체 채팅 JSONL, 원본 자막·캡션 VTT와 `{video_id}.mp3`가 여기에 해당합니다. yt-dlp 메타데이터는 한국어 번역본을 우선 요청하므로 제공되는 경우 제목·설명·챕터를 한국어로 저장하고, 제공되지 않으면 원본 또는 가용 메타데이터를 사용합니다. 영상은 기존 단일 MP4 우선 정책을 유지하되 해당 결합 포맷이 없는 영상만 영상·음성 스트림을 각각 받아 FFmpeg로 MP4 병합합니다. MP3는 별도의 `bestaudio/best` 다운로드와 최고 MP3 품질 설정으로 생성합니다.

2단계에서는 추가 메타데이터 선택 여부와 관계없이 분석·렌더링에 사용할 원본 영상을 `yt-data/{video_id}`에 확보합니다. 자막과 캡션은 각각의 체크박스를 선택한 경우에만 다운로드합니다.

`yt-edit/{video_id}`에는 2단계에서 원본을 고정된 방식으로 가공한 파일을 둡니다. 1단계 `info.json`에는 `comment_count`만 유지하고 댓글 본문 `comments`는 저장하지 않습니다. YouTube 챕터는 설명을 파싱하지 않고 한국어 로케일 페이지의 플레이어 `DESCRIPTION_CHAPTERS` 데이터를 우선 사용하며, 수집할 수 없을 때 yt-dlp 결과를 유지합니다. 대댓글을 제외한 댓글은 사용자가 댓글 자료를 선택한 경우에만 별도 수집하여 메모리에서 표시하고, 타임스탬프 댓글은 `comments-timestamps.json`, 채팅 시각은 `chat-times.json`으로 저장합니다. 자동 캡션은 롤링 중복을 제거한 `captions-rolling.vtt`와 파싱 스크립트 파일을 저장하며, 업로드 자막의 파싱 스크립트도 여기에 둡니다. `yt-data/{video_id}/{video_id}.mp3`는 최고 품질 원본으로 보존하여 향후 음량 분석에 재사용합니다. 원격 Whisper 전사에는 원본 MP3를 16 kHz·모노·64 kbps로 고정 변환해 `yt-edit/{video_id}/{video_id}.whisper.mp3`에 보존한 파일을 사용합니다. 파싱 스크립트와 Whisper 전사 파일은 모두 `{"segments":[{"start":number,"end":number,"text":string}]}` 형식이다. 작업 설정과 실행 결과에 따라 달라지는 Whisper 전사와 3·4단계 스크립트·계획·LLM 체크포인트·결과는 `yt-edit/{job_id}`에 저장합니다.

3단계는 이 파일과 이미 받은 원본 영상만 읽으며 yt-dlp 재수집이나 WebVTT 재파싱을 하지 않습니다.

## 서버 연동

원격 Whisper API는 WhisperX `large-v3` 전사와 언어별 CTC 강제 정렬을 한 번 수행하여 문장 세그먼트와 단어 타임스탬프를 함께 반환합니다. 클라이언트는 `engine=whisperx-aligned-word-v1`, `alignment=ctc-forced-alignment-with-words` 표식을 검증합니다. 공백 제외 25자를 초과한 세그먼트는 먼저 단어 사이 0.5초 이상 무음 경계에서 나눕니다. 이 경계에서는 앞 자막의 종료를 앞 단어 `end`, 뒤 자막의 시작을 다음 단어 `start`로 정해 무음 구간을 자막 표시 시간에서 제외합니다. 나뉜 조각이 여전히 25자를 초과하면 LLM에 분할 경계 단어 인덱스를 요청합니다. 목표 구간이 N개라면 LLM은 각 앞 구간의 마지막 단어 인덱스 N-1개만 오름차순으로 반환하고, 클라이언트가 누락·중복 없는 연속 단어 범위를 구성합니다. LLM 내부 분할점은 이전 단어 `end`와 다음 단어 `start`의 중간값으로 정해 앞뒤 조각의 공통 경계로 사용합니다. 원본 세그먼트의 첫 시작과 마지막 종료는 보존합니다. 짧은 세그먼트는 원래 세그먼트 시각을 유지하며 고정 오프셋은 적용하지 않습니다. 영상에 업로드 자막과 자동 캡션이 모두 없거나 사용자가 제공된 자막·캡션을 모두 선택 해제하면 Whisper를 자동 활성화하고 스크립트 소스를 고정합니다. `timestamp_mode=whisperx-aligned-word-v1` 캐시 지문으로 이전 결과를 재사용하지 않으며, 원본 API 결과는 작업 폴더에 보존합니다.

클라이언트는 서버에 인증, LLM, 원격 STT, 작업 이력 동기화를 요청합니다. 장시간 Whisper 전사 중에는 브라우저가 각 상태 조회 전에 현재 Supabase 세션을 확인하고 만료 60초 전부터 토큰을 갱신합니다. 401 응답에는 강제 갱신 후 한 번 재시도하며, 검증된 최신 토큰을 로컬 백그라운드 작업과 공유하여 heartbeat·SSE 재연결·완료 ACK·후속 LLM 요청이 시작 시점 토큰에 고정되지 않도록 합니다. 서버 URL은 `.env`의 `AVE_SERVER_URL`로 설정합니다. LLM·Whisper의 비밀 값은 클라이언트에 두지 않습니다.

원본 영상, 렌더링 결과, 로컬 경로는 서버로 보내지 않습니다. 렌더링 완료 뒤 현재 서버 API 계약이 받는 스크립트·구간 분석값·추천·선택 정보를 전송합니다.

원격 STT가 필요한 경우 보존된 Whisper 최적화 MP3만 서버 HTTP API로 업로드합니다. 로컬 Whisper와 FTP는 지원하지 않습니다.

## 개발 상태

정적 레거시 UI와 `/legacy` 경로는 사용하지 않습니다. `ui/`에서 `npm run build`를 실행하면 `static/ui/`가 갱신됩니다. 향후 사용자 배포는 pynsist 설치 프로그램이 아닌 PyInstaller 기반 Windows 포터블 앱으로 진행하고 관련 설정과 산출물은 `ave-dist`에서 관리합니다. 현재 패키징은 구현하지 않았으며 개발 실행은 `python -m app`을 기준으로 유지합니다.

## 로컬 SQLite 저장소

`db/ave-client.sqlite3`는 완료된 결과 영상의 최소 조회 정보만 저장합니다. 진행 상태, 전사본, 스크립트, LLM 응답 및 후보 점수는 SQLite에 저장하지 않습니다. 분석 중 전사·스크립트·계획·LLM 체크포인트와 렌더링 SRT·결합 영상·인코더별 시도 영상·pending 영상은 `yt-edit/{job_id}`에 저장하며 성공·취소·실패·중단 뒤에도 자동 삭제하지 않습니다. 최종 영상과 JSON은 같은 디렉터리의 임시 파일을 거쳐 원자적으로 교체합니다. 일반 중단 작업은 자동 복원하지 않지만, LLM 계약 오류가 20회 연속 발생해 일시중지된 작업은 체크포인트 기반 명시적 재개를 지원합니다.

개발 단계에서는 테스트·개발 실행으로 생성된 `media/` 작업물과 `db/` SQLite DB를 보존하거나 이전 파일 구조와 호환하지 않습니다. 저장 구조가 바뀌면 기존 작업물을 삭제하고 새 작업으로 검증합니다.
