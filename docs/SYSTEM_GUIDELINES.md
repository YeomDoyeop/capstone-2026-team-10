# AVE 시스템 개발 가이드라인

## 목적과 적용 범위

이 문서는 AVE의 전체 시스템 구조, 주요 데이터 처리 흐름, 저장 대상의 상위 기준을 정의한다. 기존 프로젝트 및 모듈 문서를 대체하지 않으며, 모듈별·기능별 문서는 이 문서와 실제 코드 및 계약을 함께 참고한다.

여기서 정하지 않은 세부 구현, 데이터 모델, API 계약은 확정 요구사항으로 간주하지 않는다. 구현 중 새로 결정한 내용은 해당 모듈 문서에 기록하고, 전체 구조에 영향을 주면 이 문서도 갱신한다.

## 시스템 구성

| 구성 요소 | 역할 |
| --- | --- |
| 사용자 | 클라이언트 웹 UI로 작업을 시작하고 분석·편집 결과를 선택한다. |
| `ave-client` | 영상과 관련 데이터를 로컬에서 획득·관리하고, 필요한 원격 처리를 서버에 요청한다. SQLite와 yt-dlp·FFmpeg 독립 바이너리를 사용한다. |
| `ave-server` | 인증, 작업·분석 데이터 관리, 외부 LLM API 호출과 원격 STT 중계를 담당한다. |
| `ave-whisper-api` | 서버가 전달한 전사용 음성을 처리해 스크립트와 시간 구간을 생성한다. |

서버 구현에서는 Supabase를 인증 및 데이터 저장 기반으로 사용할 수 있으며, LLM과 STT는 외부 또는 별도 서비스로 분리한다.

## 처리 흐름

### URL 입력과 로컬 수집

사용자가 UI에 URL을 입력하면 클라이언트는 yt-dlp를 이용해 이용 가능한 범위에서 영상, 음성 및 메타데이터를 수집한다. 메타데이터에는 제공되는 경우 스크립트 또는 캡션, 자막, 채팅 리플레이, 히트맵, 챕터, 댓글이 포함된다. 클라이언트는 음성에서 음량 데이터도 추출한다.

각 메타데이터는 원본 영상 또는 플랫폼이 실제로 제공하는 경우에만 수집한다.

### 선택적 원격 STT

기존 스크립트를 사용할 수 없거나 원격 전사가 필요한 경우, 클라이언트가 전사용 음성 파일을 서버에 전달한다. 서버는 STT 서비스에 요청하고, 반환된 스크립트를 관리한 뒤 클라이언트에 전달한다. 임시 전사용 음성의 보관 기간과 삭제 방식은 현재 아키텍처 및 서버 API 계약을 따른다.

### 스크립트 분석

1. 클라이언트는 전체 스크립트를 서버로 전달하고, LLM은 같은 중심 논점의 질문·답변·근거·결과를 유지하는 가능한 큰 상위 주제 단위로 챕터를 분할한다.
2. 각 챕터는 다시 독립적으로 처리해 질문·답변·주장·근거·사례·원인·결과처럼 선택 판단이 달라지는 가능한 작은 의미 단위의 섹션과 중요도 점수를 생성한다.
3. LLM에 주고받는 문장 및 구간 데이터는 JSONL을 기본 교환 형식으로 사용한다.

문장 입력 항목은 `index`, `text`를 가지며, 챕터·섹션 항목은 `start_index`, `end_index`, `summary`를 가진다. 문장 중요도는 `index`, `score`로 반환하며 점수 범위는 0부터 1000까지이다.

### 점수 종합과 최소 필수 관계 확장

문장별 최종 점수는 LLM 중요도, 채팅 빈도, 타임스탬프 댓글 수, 히트맵, 음량 피처를 정규화해 조합한다. 조합은 사용자 지정 순서 기반 배율, 직접 배율 지정, 향후 학습 데이터를 활용한 자동 설정을 지원 대상으로 둔다.

현재 타임스탬프 댓글은 댓글 원문의 목적과 관심 강도를 LLM의 0~1000 정수 계약으로 평가하고, 검증 직후 `0.0~1.0`으로 정규화해 섹션 배지로 표시한다. LLM 중요도 점수도 같은 방식으로 정규화해 저장·표시한다. 채팅은 영상별 익명 작성자 ID와 원본 시각만 보관하되 점수 계산 시 반응 지연 보정으로 3초 앞당긴다. 최초 30초를 제외한 뒤, 기준선이 완성되는 다음 3분 동안 영상 전체 밀도와 확보된 지역 기준선을 점진적으로 혼합하고 이후에는 30초 이동창을 직전 3분과 비교한다. 음량은 최초 30초를 워밍업 기준선으로만 사용한 뒤 1초 RMS를 3초 평활해 직전 30초보다 3dB 이상 커진 2초 이상의 상승을 평가한다. 채팅·음량은 P50~P95 기준으로 `0.0~1.0` 정규화하고 섹션 상위 10% 평균 70%와 전체 평균 30%로 집계한다. 섹션 총점은 히트맵·댓글·섹션 LLM·챕터 LLM·채팅·음량 순서로 `0.25·0.20·0.18·0.15·0.12·0.10` 가중치를 적용하며, 없는 특성은 제외하고 남은 가중치 합으로 재정규화한다. 배지는 주황색 총점을 가장 왼쪽에 두고 `◀` 뒤에 바이올렛 히트맵·브라운 댓글·녹색 섹션 LLM·노란색 채팅·빨간색 음량 순서로 표시한다. 챕터 LLM은 파란색이다. 표시값만 소수점 셋째 자리에서 반올림한다.

모든 점수 특성은 입력 영상에서 지원되고 사용자가 현재 작업에서 선택한 경우에만 계산하고 표시한다. 지원되지 않거나 선택하지 않은 특성에는 점수 필드나 UI 배지를 만들지 않는다. 별도의 사용자 선택 항목이 없는 특성은 유효한 원본 데이터가 존재할 때만 활성화한다.

최종 점수가 높은 섹션부터 차례로 반드시 보존할 핵심 지점으로 선정하고 그 섹션이 속한 챕터 전체를 LLM에 전달해 필수 연결만 가장 적게 찾는다. 요청에는 `allowed_ids`를 두지 않는다. 관계 응답은 입력 배열 위치의 원본 시간순 정수 `indexes` 배열만 받으며 앵커 위치 반환도 허용한다. 클라이언트가 인덱스를 실제 섹션 ID로 복원한다. 동일 입력의 응답은 체크포인트로 재사용하고 계약 실패는 최대 100회 시도한다.

## 데이터 저장 원칙

### 서버

서버에는 사용자 인증 정보와 렌더링을 완료한 작업·분석 데이터를 저장한다. 저장 범위는 현재 서버 API와 스키마를 기준으로 하며 작업 또는 영상 식별자, 스크립트, 구간 분석값, 추천·선택 정보를 포함한다. 클라이언트의 로컬 경로와 진행 중·실패·취소 상태는 저장하지 않는다. 기승전결 탐색 너비와 깊이는 해당 기능 구현 시 저장 여부를 정한다.

원본 영상, 렌더링 결과, 클라이언트의 로컬 경로는 서버의 영구 저장 대상이 아니다. 원격 STT용 음성은 처리에 필요한 임시 데이터이며, 영구 분석 데이터와 구분한다.

### 클라이언트

영상, 음성, 메타데이터, 스크립트 및 작업 중 생성되는 관련 파일은 로컬 파일로 보관한다. 한 영상에서 항상 동일한 원본은 `yt-data/{video_id}`, 고정된 처리로 생성되어 항상 동일한 파생 자료는 `yt-edit/{video_id}`, 작업마다 달라질 수 있는 자료는 `yt-edit/{job_id}`에 둔다.

`{video_id}.mp3`는 yt-dlp로 이용 가능한 최고 품질 오디오를 별도로 받아 `yt-data/{video_id}`에 생성하고 완료 후에도 보존한다. 영상 다운로드 형식은 현행 정책을 유지한다. 향후 음량 분석에는 이 원본을 사용한다. 원격 Whisper 전사에는 원본 MP3를 16 kHz·모노·64 kbps로 고정 변환한 `yt-edit/{video_id}/{video_id}.whisper.mp3`를 사용하며, 이 파생 파일도 완료 후 삭제하지 않고 재사용한다. 작업별 전사·분석 스크립트·계획·LLM 체크포인트·결과와 렌더링 임시 산출물은 `yt-edit/{job_id}`에 두며 성공·취소·실패·중단 여부와 관계없이 자동 삭제하지 않는다. 최종 영상과 JSON은 같은 디렉터리에서 원자적으로 교체한다. SQLite에는 렌더링 완료 작업만 저장하고 진행 상태는 저장하거나 자동 복원하지 않는다. 단, LLM 재시도 소진 작업은 보존된 체크포인트를 이용해 사용자가 명시적으로 재개할 수 있다.
