# AVE Client

AVE Client는 사용자의 Windows PC에서 영상 편집을 수행하는 클라이언트 모듈이다. 원본 영상과 렌더링 결과는 로컬 `media/`에만 보관한다.

## 책임

* React 웹 UI와 로컬 FastAPI 서버 실행
* yt-dlp로 YouTube 메타데이터·영상·댓글·채팅·자막·캡션 수집
* FFmpeg로 구간 편집, 음원 추출, 자막 합성, 결과 렌더링
* AVE Server를 통한 로그인 검증, LLM·원격 Whisper 호출, 작업 이력 동기화
* 완료된 결과만 로컬 SQLite 및 AVE Server 이력에 동기화
* 시스템 트레이에서 UI 열기·독립 클라이언트 로그 GUI 확인·종료 제공. 로그는 파일에 보존하는 동시에 메모리 링 버퍼를 통해 GUI에 전달

클라이언트는 원본 영상, 렌더링 영상, 로컬 경로, 서버 API 키, Supabase 서비스 키를 서버로 보내지 않는다.

## 요구 환경

* Windows x64
* Python 3.11 이상
* AVE Server URL
* `/bin/yt-dlp.exe`, `/bin/ffmpeg.exe`, `/bin/ffprobe.exe`

개발 환경에서 영상 도구를 받으려면 다음을 실행한다.

```powershell
powershell.exe -ExecutionPolicy Bypass -File .\scripts\fetch-tools.ps1
```

도구 배치·업데이트·배포 전 확인 항목은 [docs/TOOLCHAIN.md](docs/TOOLCHAIN.md)를 참고한다.

## 설정

`.env.example`을 복사해 `.env`를 만들고 AVE Server 주소만 설정한다.

```env
AVE_SERVER_URL=https://ave-server.example.com
WHISPER_HEARTBEAT_SECONDS=10
```

`YTDLP_COOKIES_FROM_BROWSER`, `YTDLP_COOKIEFILE`, `YTDLP_PLAYER_CLIENT`, `YTDLP_FORMAT`은 YouTube 수집 문제를 조정할 때만 선택적으로 사용한다.

Supabase 공개 로그인 설정과 LLM·Whisper 자격 증명은 AVE Server가 관리한다. 클라이언트 `.env`에 저장하지 않는다.

기본 LLM은 DeepSeek-V4-Flash(내부 API 모델 식별자 `deepseek-chat`)이며 UI·API·Gateway의 기본값이 같다. Gemini 3.5 Flash-Lite도 같은 JSON 응답 계약과 공통 Gateway로 선택할 수 있다. 병렬 정책은 공급자별로 분리한다. DeepSeek-V4-Flash는 작업당 최대 20개의 독립 요청을 병렬 실행하고 요청 시작 사이를 0.05초 이상 둔다(초당 최대 약 20건 제출, 초당 20건 완료를 보장하는 값은 아님). 재시도도 같은 간격 제한을 적용한다. Gemini는 새 원격 커밋의 유료 프로젝트 설정을 반영해 최대 50개 병렬·요청 간격 0.015초를 사용한다. AVE Server도 한 프로세스에서 Gemini 요청 시작을 4,000 RPM 이내로 제한한다. 이는 모든 계정의 보장 한도가 아니며 TPM·일일·지출 한도와 다중 서버 프로세스는 별도 관리가 필요하다. 병렬 수 증가는 처리 속도를 위한 변경이며 502 오류를 해결하지 않고, 공급자 부하나 429 오류를 늘릴 수도 있다. 일시적인 통신·서버 오류는 대기 후 제한적으로 재시도하고, 해결되지 않으면 원인을 화면에 표시한다. Whisper 초기 프롬프트와 핫워드는 기본적으로 비활성화한다. 초기 프롬프트를 켜면 LLM을 사용하지 않고 선택 언어별 내용 중립적인 문장부호 예시를 고정 적용하며, 자동 언어 감지에서는 언어 편향을 피하기 위해 비워 둔다. 핫워드를 켜는 시점에만 LLM을 한 번 호출하여 메타데이터 원문에 실제 존재하며 특정 대상을 식별하는 고유명사를 개체 유형과 함께 판정하고, 검증을 통과한 항목을 최대 10개·항목당 40자로 입력한다. 각 옵션을 끄면 입력란을 숨기고 전사 요청에도 보내지 않는다. 사용자가 핫워드를 수정한 뒤 `초기화`를 누르면 최초 자동 생성값으로 되돌린다.

렌더링 자동 모드는 FFmpeg가 포함한 `h264_nvenc`(NVIDIA), `h264_amf`(AMD), `h264_qsv`(Intel) H.264 인코더를 이 순서로 실제 렌더링에 시도한다. 한 GPU가 드라이버·장치·필터 호환성으로 실패하면 남은 GPU 후보를 계속 시도하고, 모두 실패한 경우에만 CPU `libx264`로 처음부터 다시 렌더링한다. GPU 인코더를 선택한 영상 재인코딩은 입력에도 `-hwaccel auto`를 적용해 하드웨어 디코딩을 우선 시도한다. 자막 합성·구간 trim처럼 CPU 필터가 필요한 단계는 FFmpeg가 안전하게 프레임을 전송해 처리한다. 렌더링 진행 메시지와 완료 메시지에는 실제로 사용한 GPU 또는 CPU 방식을 표시한다. `AVE_VIDEO_ENCODER=cpu`로 GPU를 끌 수 있고, 특정 인코더 이름을 지정하면 해당 인코더만 시도한 뒤 CPU로 전환한다. 오디오 추출과 스트림 복사는 영상 재인코딩이 아니므로 하드웨어 가속 대상이 아니다.

구간 자르기·결합과 자막 합성은 하나의 FFmpeg 필터 그래프에서 처리하여 최종 영상을 한 번만 인코딩한다. 인코더별 임시 시도 영상은 성공·실패·취소 후 제거한다.

이미 종료된 작업에 브라우저가 뒤늦게 취소를 요청해도 취소 API는 성공으로 응답한다. `yt-edit/{job_id}`의 작업 파일은 취소·실패 뒤에도 자동 삭제하지 않는다.

렌더링 등 실행 중 오류는 SSE로 원인을 한 번 전달한 뒤 작업 폴더·메모리·토큰을 정리한다. SSE 단절로 이 마지막 메시지를 받지 못한 경우 UI는 상태 조회의 404를 종료·정리됨으로 표시한다.

4단계 렌더링은 SRT와 pending 영상을 `yt-edit/{job_id}` 안에 고유한 이름으로 생성한다. 구간 결합과 자막 합성은 한 번의 렌더링으로 수행하며 인코더별 임시 시도 영상은 실행 뒤 제거한다. 완성된 pending 영상은 별도의 같은 디렉터리 파일로 복사한 뒤 `os.replace`로 최종 영상을 원자적으로 교체한다. 기본 번인 자막은 Dotum 16, 하단 여백 12, 한 줄 30자 줄바꿈을 사용하며 0.08초 미만으로 표시되는 자막은 제외한다. YouTube 롤링 캡션의 완료 표식은 직전 완료 표식부터 현재 완료 시점까지의 실제 표시 구간으로 복원한 뒤 분석과 렌더링에 사용한다. 캡션에서 `[음악]`, `(박수)`, `[Music]`처럼 비언어 설명만 있는 구간과 음표 기호만 있는 구간은 제외하고, 발화 앞의 `>>`, `＞＞`, `≫` 전환 기호는 기호만 제거한다. 이 처리는 업로드 자막 원문에는 적용하지 않는다. FFmpeg 자막에는 드라이브·경로 구분자를 이스케이프한 절대 경로를 전달하며 Windows 임시 폴더는 사용하지 않는다. 렌더링이 성공하면 서버 이력 동기화가 실패해도 결과 영상과 로컬 완료 이력은 유지하며, UI에는 서버가 반환한 동기화 실패 원인을 표시한다.

하단 진행 메시지는 긴 로그가 화면 밖으로 넘치지 않도록 끝부분을 흐리게 표시한다. 메시지를 세 번 클릭하면 브라우저의 문단 선택으로 숨겨진 부분을 포함한 전체 로그를 선택·복사할 수 있다.

## 장시간 작업 추적과 취소

작업 ID는 1단계에서 2단계로 넘어가며 추가 자료 다운로드를 시작할 때 한 번 확정하고 `<video_id>.<unix_timestamp_hex>` 형식을 사용한다. 이후 추가 자료 재수집, Whisper 재수행, 분석과 렌더링은 모두 같은 ID를 사용한다. 진행 중 상태는 프로세스 메모리에만 존재하며 새로고침·프로세스 재시작·취소·일반 실패 시 복원하지 않는다. `yt-edit/{job_id}`의 작업 파일은 취소·실패·중단 뒤에도 보존한다. LLM 응답이 3회 시도 후에도 계약을 충족하지 못하거나 API 오류를 자동 복구하지 못하면 원인을 구분해 작업을 일시중지하며, 진행 도크의 기존 `작업 취소` 자리를 `재시도` 버튼으로 교체한다. 사용자가 재시도하면 저장된 LLM 체크포인트를 재사용한다. 결과 영상 생성이 성공한 작업만 SQLite와 AVE Server 이력에 저장한다.

완료 작업은 활성 작업 복구 대상이 아니다. 결과 조회 화면에서 **처음**을 누르면 메타데이터 단계로 돌아가며, 새 편집은 새 작업 ID로 시작한다.

## 로컬 파일 경계

파일 경로는 생성 시점이나 임시 여부가 아니라 내용이 결정되는 단위를 기준으로 선택한다.

* 한 영상에서 항상 동일한 원본 자료: `yt-data/{video_id}`
* 고정된 처리로 생성되어 같은 영상에서 항상 동일한 파생 자료: `yt-edit/{video_id}`
* 작업 설정·외부 응답·사용자 선택·실행 결과에 따라 달라질 수 있는 자료: `yt-edit/{job_id}`

`yt-data/{video_id}`는 yt-dlp가 만든 원본만 보관하며 재작업 때 그대로 재사용한다. `{video_id}.info.json`은 yt-dlp 저장 직후와 기존 캐시 재사용 시점에 댓글 본문 `comments`를 제외하고 UTF-8·2칸 들여쓰기 형식으로 원자적 재저장한다. 댓글 개수와 자막·캡션 트랙 목록 같은 공개 메타데이터는 유지하며, 실제 댓글 본문은 사용자가 댓글 자료를 선택한 경우에만 별도 파일로 수집한다. `yt-edit/{video_id}`는 2단계에서 원본으로부터 만든 재사용 가능한 자막·캡션 및 메타데이터 자료이고, 완료·실패와 관계없이 보존한다. 작업별 `yt-edit/{job_id}`에는 Whisper 전사, 분석 스크립트·계획·LLM 체크포인트와 최종 영상을 둔다.

| 위치 | 파일 | 역할 |
| --- | --- | --- |
| `yt-data/{video_id}` | `{video_id}.info.json`, 댓글 JSON, 채팅 JSONL, 자막·캡션 VTT, `{video_id}.mp3` | yt-dlp 원본과 최고 품질 공용 오디오 |
| `yt-edit/{video_id}` | `{video_id}.comments-timestamps.json`, `{video_id}.chat-times.json`, `{video_id}.whisper.mp3` | 분석·전사용 파생 메타데이터 |
| `yt-edit/{video_id}` | `{video_id}.{lang}.captions-rolling.vtt`, `*.{subtitles,captions}-transcript.json` | 표시용 롤링 캡션과 파싱 스크립트 |
| `yt-edit/{job_id}` | Whisper 전사, 분석 계획·LLM 체크포인트, SRT·결합·인코더 시도·pending 영상, `{job_id}.edited.mp4` | 작업별 자료와 산출물 |

`{video_id}.mp3`는 yt-dlp의 `bestaudio/best` 선택과 최고 MP3 품질 설정으로 별도 다운로드해 `yt-data/{video_id}`에 둔다. 영상 다운로드 형식은 기존 정책을 유지한다. 원본 MP3는 향후 음량 분석에 재사용하고, Whisper 전사에는 이를 16 kHz·모노·64 kbps로 고정 변환한 `yt-edit/{video_id}/{video_id}.whisper.mp3`를 사용한다. 두 MP3는 완료 후에도 삭제하지 않으며, 전사용 파일은 이미 있으면 다시 변환하지 않는다. WhisperX 원본 전사는 원본 오디오의 크기·수정 시각, 언어·초기 프롬프트·핫워드·배속, 엔진·정렬 계약으로 만든 설정 해시를 사용해 `yt-edit/{video_id}/whisper-cache`에 보존한다. 새 작업에서도 같은 지문의 유효한 결과가 있으면 오디오 업로드와 RunPod 전사를 건너뛰고 작업별 `{job_id}.whisper-source.json`으로 복사한다. 최종 문장 분할 결과도 원본 전사 지문·LLM 공급자·분할 계약의 해시로 같은 공유 캐시에 보존하며, 일치하는 결과가 있으면 LLM 분할을 생략하고 작업별 `{job_id}.whisper-transcript.json`으로 복사한다. 작업 중 LLM 체크포인트는 계속 `{job_id}`에 저장한다.

분석은 2단계에서 준비한 자료만 읽으며 yt-dlp 재수집이나 VTT 재파싱을 하지 않는다. 2단계 다음에는 4단계 UI로 바로 이동한다. 4-1에서 소스를 선택하면 자막·캡션 또는 같은 `job_id`의 Whisper 전사를 문장 단위로 표시한다. **분할**을 누르면 챕터·섹션 분할과 섹션 중요도·히트맵·댓글·채팅·음량 및 종합 점수를 한 작업에서 계산한다. 4-2는 4-3과 같은 챕터·섹션 점수 화면을 표시하되 선택을 잠그고 목표 길이만 수정할 수 있다. **다음**을 누르면 체크포인트의 분할·점수를 재사용하고 챕터 내 필수 관계 링크만 판별한 뒤, 4-3에서 추천 결과와 선택 기능을 활성화한다. 모든 LLM 요청·응답의 ID는 정수형만 사용한다. 애플리케이션 내부 섹션 키가 문자열이어도 요청별 0부터 시작하는 정수로 변환해 보내고 응답 검증 후 원래 키로 복원한다. 중요도 평가는 챕터별 summary와 섹션 `[{"id","text"}]` 배열을 최대 32개씩, 공급자별 입력 길이 예산에 맞춰 묶어 보내고 같은 정수 ID의 `[{"id","score"}]` 배열만 받는다. 타임스탬프 댓글은 전체를 한 번에 `[{"index","text"}]`로 보내 목적과 관심 강도에 따른 `[{"index","score"}]`를 받고, 댓글 안의 모든 시각이 속한 섹션에 점수를 적용한다. JSON 문법·ID·순서·개수·범위 계약이 틀리면 거부 이유를 전달해 최대 3회 시도한다. 섹션 점수 검증도 재시도와 체크포인트 저장 전에 수행한다. 재시도 소진 시 작업을 일시중지하고 명시적 재개 때 체크포인트를 사용한다. 독립 요청은 공급자별 제한을 적용한다.

자막·캡션 파싱 파일과 Whisper 전사 파일은 모두 `{"segments":[{"start":number,"end":number,"text":string}]}` 형식이다. 영상에 업로드 자막과 자동 캡션이 없거나, 제공되더라도 사용자가 두 자료를 모두 선택 해제하면 Whisper STT를 자동 활성화하고 스크립트 소스를 `whisper_api`로 고정한다. 자막이나 캡션 중 하나를 다시 선택해야 Whisper를 선택적으로 끌 수 있다. 분석 시작 API도 영상 자체에 두 스크립트가 없는 조건을 다시 확인한다. Whisper 전사 배속은 `1.0 (품질)`, `1.5 (균형)`, `2.0 (속도)`만 선택할 수 있으며 기본값은 품질이다. YouTube 챕터는 설명의 타임스탬프 문구를 파싱하거나 번역해 만들지 않는다. 한국어 로케일(`hl=ko`, `gl=KR`)의 YouTube 페이지가 플레이어용 `DESCRIPTION_CHAPTERS` 데이터로 직접 제공한 제목과 시각을 우선 저장하고 UI에 표시한다.

Whisper API는 WhisperX `large-v3` 전사 후 언어별 CTC 음향 모델로 한 번 강제 정렬하여 세그먼트와 그 안의 단어 타임스탬프를 함께 반환한다. 클라이언트는 `engine=whisperx-aligned-word-v1`, `alignment=ctc-forced-alignment-with-words`를 검증한다. 공백 제외 30자 미만 세그먼트는 원래 세그먼트 시각을 그대로 사용한다. 30자 이상인 세그먼트는 먼저 단어 사이 0.5초 이상 무음 경계에서 나누고, 앞 자막의 종료는 앞 단어 `end`, 뒤 자막의 시작은 다음 단어 `start`로 정한다. 이렇게 나눈 조각이 여전히 30자 이상이면 LLM에 자막용 분할임과 공백 제외 약 30자가 자막 한 줄의 대략적인 분량임을 알려 분할 경계 단어 인덱스를 요청한다. 30자는 강제 경계가 아니며 목표 개수도 전달하지 않는다. LLM은 자막 가독성과 문법·의미 경계를 기준으로 필요한 분할 수를 정한다. 자연스러운 분할을 확신하기 어려우면 빈 `indexes` 배열을 반환해 원문을 유지할 수 있다. 독립된 Whisper 세그먼트의 분할 요청은 섹션 점수 평가와 동일한 공급자별 제한으로 병렬 실행하고 결과는 원본 순서로 재조립한다. LLM이 경계를 선택하면 각 앞 구간의 마지막 단어 인덱스를 오름차순 정수로 반환하고, 클라이언트가 중복 없는 연속 단어 범위를 구성한다. LLM 경계는 이전 단어 `end`와 다음 단어 `start` 사이의 중간값으로 정해 앞뒤 자막이 같은 경계에서 맞닿게 한다. 원본 세그먼트의 첫 시작과 마지막 종료는 보존한다. 원본 API 결과는 `{job_id}.whisper-source.json`에 보존하며 `timestamp_mode=whisperx-aligned-word-v1` 캐시 지문으로 이전 결과의 재사용을 차단한다.

Whisper 전사 중에는 `WHISPER_HEARTBEAT_SECONDS`마다 AVE Server에 heartbeat를 보낸다. 브라우저는 각 상태 조회 전에 현재 Supabase 세션을 확인하고 만료 60초 전부터 토큰을 갱신하며, 401 응답에는 강제 갱신 후 한 번 재시도한다. 인증된 상태 조회에 사용된 최신 토큰은 같은 사용자의 로컬 백그라운드 작업에 전달되어 이후 heartbeat·SSE 재연결·완료 ACK·후속 LLM 요청에 사용된다. 클라이언트는 세그먼트 결과를 성공적으로 저장한 뒤 ACK를 보내며, ACK가 네트워크 오류로 실패해도 서버는 기본 15분 동안 완료 결과를 보관해 SSE 재연결이 다시 받을 수 있게 한다. ACK 또는 TTL 만료 뒤 전사 제어 레코드는 삭제된다. 로컬 클라이언트 자체가 종료되거나 네트워크가 끊기면 heartbeat가 멈추며, 서버의 lease 만료 정책이 RunPod 작업·임시 MP3·실행 제어 레코드를 정리한다. 사용자가 UI의 **작업 취소**를 누르면 전사 준비 단계에서도 `client_job_id` 기준 취소 의도를 서버에 먼저 전달한다. 서버는 RunPod 작업 ID가 아직 없더라도 이를 확인해 요청을 건너뛰거나 즉시 취소한다. 이 제어 정보는 완료 이력이 아니며 처리 또는 만료 뒤 삭제된다. 다운로드·FFmpeg·전사처럼 동기 실행 중인 로컬 구간은 다음 진행도 보고 지점에서 협력적으로 취소된다.

챕터·섹션 구조화에서 챕터는 가능한 큰 상위 주제 단위로 만든다. 같은 중심 질문·사건·논점 안의 질문과 답변, 주장과 근거, 원인과 결과는 같은 챕터에 유지하고 명백한 상위 주제 전환에서만 나눈다. 섹션은 질문·답변·주장·개별 근거·사례·반론·원인·결과·결론처럼 독립적으로 선택할 수 있는 가능한 한 작은 의미 단위로 나눈다. 문법적으로 끝나지 않은 조각은 만들지 않되, 서로 다른 담화 기능을 한 섹션에 합치지 않는다.

## 점수 표시

히트맵 점수는 yt-dlp 히트맵 각 시간 구간의 중앙을 실제 표본점으로 보고 인접 표본 사이를 선형 보간한다. 섹션 시작·끝의 추정값과 섹션 내부 실제 표본값 중 최댓값을 `0.0~1.0` 범위로 저장하고, 4단계에서 LLM 점수 오른쪽·댓글 점수 왼쪽에 붉은색 배지로 표시한다. 히트맵 자료가 없으면 배지를 표시하지 않는다. 히트맵 점수는 아래 가중치로 총점과 추천 계산에 반영한다.

채팅 분석 파일에는 메시지나 원본 작성자 정보를 저장하지 않고 `elapsed_seconds`와 영상 단위 SHA-256 익명 `author_id`만 저장한다. 원본 시각은 보존하며 점수 계산에서만 사람의 반응·입력 지연을 고려해 3초를 차감하고 0초 미만은 0초로 제한한다. 채팅 점수는 최소 10건일 때 5초마다 최근 30초의 채팅량을 직전 3분 기준선과 비교한다. 최초 30초에는 점수를 부여하지 않고, 이후 3분 동안은 확보된 지역 기준선과 영상 전체 채팅 밀도를 기준선 확보 비율로 혼합하며, 그 뒤에는 직전 3분만 사용한다. 작성자별 이동창 기여는 최대 3건으로 제한하고 전체 채팅 수와 고유 작성자 수를 같은 비중으로 반영하며, 상대 증가 60%와 영상 내 채팅량 백분위 40%를 결합한다. 음량 점수는 최고 품질 원본 MP3의 1초 RMS(dBFS)를 3초 중앙값으로 평활한 뒤 직전 30초 중앙값 대비 3dB 이상, 절대 -45dBFS 이상인 상승이 2초 이상 이어질 때 계산한다. 최초 30초는 기준선 수집용 워밍업 구간으로 두어 음량 급증 점수를 부여하지 않는다. 두 점수 모두 영상 내 P50을 0, P95를 1로 정규화하고 섹션의 상위 10% 평균 70%와 전체 평균 30%를 합친다. 음량은 노란색, 채팅은 주황색 배지로 표시한다.

모든 점수 특성은 영상에서 지원되고 현재 작업에서 선택한 경우에만 계산·표시한다. 지원되지 않거나 선택하지 않은 특성은 점수 필드와 배지를 모두 생성하지 않는다. 채팅은 메타데이터 다운로드에서 선택한 경우만 계산한다. 별도 선택 항목이 없는 히트맵과 음량은 각각 유효한 원본 데이터와 오디오 분석 결과의 존재를 선택 조건으로 간주한다.

섹션 총점은 `[히트맵, 댓글, 섹션 LLM, 챕터 LLM, 채팅, 음량]`에 각각 `[0.25, 0.20, 0.18, 0.15, 0.12, 0.10]`을 곱해 선형 결합한다. 다수 시청자의 실제 반복 시청 행동인 히트맵을 가장 높이고, 장면을 명시적으로 지목한 댓글을 다음으로 둔다. 섹션 LLM과 챕터 LLM은 내용과 문맥의 중요도를 보완하고, 반응 지연과 영상 유형의 영향을 더 받는 채팅 및 음량은 상대적으로 낮은 비중을 사용한다. 지원되지 않거나 선택하지 않은 특성의 가중치는 제외하고 남은 가중치 합으로 나누어 재정규화하므로, 자료가 없다는 이유로 총점이 낮아지지 않는다. 총점은 주황색 배지로 가장 왼쪽에 표시하고 `◀` 기호 뒤에 히트맵·댓글·섹션 LLM·채팅·음량 배지를 둔다.

요약본 선택은 총점이 높은 섹션부터 차례로 앵커로 삼는다. 같은 챕터의 섹션 전체를 LLM에 전달하고 내용을 완전하게 이해하는 데 필수적인 연결만 최소로 고르게 한다. 요청에는 별도의 `allowed_ids`를 보내지 않는다. 응답은 입력 배열의 위치를 나타내는 원본 시간순 정수 `indexes` 배열만 받으며, 앵커 위치 반환도 허용한다. 클라이언트가 인덱스를 실제 섹션 ID로 복원한다. 같은 챕터에서 앞선 앵커가 이미 섹션을 선택했더라도 다음 고득점 섹션을 다시 앵커로 판단할 수 있으며, 선택된 전체 길이가 목표 시간을 초과하면 탐색을 중단한다. 모든 LLM 응답과 영상별 음량 분석 점은 작업 체크포인트에 저장한다.

LLM에는 세밀한 판별을 위해 LLM 중요도와 댓글 점수를 `0~1000` 정수로 요청한다. 응답 계약을 검증한 직후 1000으로 나누며, 분석 계획 저장·서버 동기화에는 히트맵과 동일한 `0.0~1.0` 정규화 값을 사용한다. UI 표시에만 소수점 셋째 자리에서 반올림한 두 자리 값을 사용한다.

## 프롬프트 파일

### 메뉴별 레시피 요약 저장

주 요리 판별은 상세 레시피 추출보다 먼저 수행한다. `recipe_menu_scan.json`으로 제목·설명·전체 자막의 모든 묶음에서 주 요리 후보와 부재료 관계를 수집하고, `recipe_menu_plan.json`으로 이를 통합하여 주 요리 목록·개수를 확정한다. 상세 추출의 `menu_name`은 확정 목록의 JSON Schema enum 및 검증 코드로 제한하므로 고추장·소스 등을 새로운 메뉴로 추가할 수 없다. 고추장 자체 만들기가 영상의 목적이라면 전역 판별에서 독립 주 요리로 인정할 수 있으며, 메뉴 개수는 2개로 하드코딩하지 않는다. `recipes.json`의 `main_menu_plan`에 개수·이름·부재료·근거 자막 ID·불확실성을 함께 저장한다. 동일 이름의 메뉴 변형 통합 및 실제 조리 순서의 정확도는 여전히 LLM과 원본 자막 품질에 의존한다.

저장된 `yt-data/<video_id>/thumbnails/`의 2MB 이하 JPEG를 Gemini로 관찰하여 제목·자막과 함께 참고한다. 상세 분석에서 DeepSeek를 선택해도 **썸네일만 Gemini를 추가 호출**하며 별도 사용량이 발생한다. `ave-server`의 이미지 전달 API 재배포 및 서버의 Gemini 키가 필요하다. 이미지는 `inlineData`로 일시 전달하고 DB·로그에 저장하지 않는다. 서버의 `image_used` 응답을 확인하며, 구버전 서버·키 오류·이미지 부재 등으로 분석할 수 없으면 `video_context.thumbnail.status=unavailable` 및 이유를 출력에 기록하고 제목·전체 자막만으로 계속한다. 썸네일을 보지 않았는데 보았다고 처리하지 않는다. 썸네일의 접시 수나 제목 숫자만으로 메뉴 개수를 확정하지 않는다. 원격 배포는 로컬 코드 수정만으로 자동 수행되지 않는다.

레시피 검증 오류는 `레시피 묶음 N/M: recipes[i].steps[j].source_ids`처럼 잘못된 위치와 기대 형식을 표시하고 재시도 지침으로 전달한다. 로그에는 원문 응답 대신 해당 진단만 기록한다. `uncertainties`의 단일 문자열은 내용 그대로 배열로 감싸고, 누락·null은 '모델이 확인 필요 사항을 제공하지 않았음'이라는 검토 표시를 남긴다. 빈 메뉴명·빈 조리 단계·잘못된 근거 ID·추가 필드는 임의로 보정하거나 버리지 않고 거부한다. 프롬프트는 내용이 없는 구간에 `recipes: []`를 명시하며, 이전 오류의 실제 필드를 원본 응답 없이 소급해서 확정할 수는 없다. 새 프롬프트·스키마는 기존 체크포인트와 구분된다.

요리·음식(`cooking_food`)을 선택하면 문장 분리 후 `prompts/system/recipe_summary.json`으로 **원본 전체 자막**의 메뉴별 레시피를 추출한다. `app/services/recipe_summary.py`는 최대 80문장·약 8,000자씩 보내며 기존 메뉴 이름을 다음 요청에 전달한다. 단일 문장은 잘라내지 않으므로 긴 문장은 예산을 초과할 수 있다. 메뉴를 최초 근거 등장 순서로 `recipe_index`(1부터), 각 메뉴의 조리 설명을 `step_index`(1부터)로 저장한다. 단계에는 재료 설명/손질/조리/완성 역할과 근거 자막 ID·원본 초 단위 시간 구간이 포함된다. 알려지지 않은 메뉴·분량이나 회상으로 인한 순서 혼동은 `uncertainties`에 표시하도록 지시한다. 이는 자막 기반 LLM 요약이며 실제 음성과의 일치·메뉴 분리·조리 순서의 정확성을 보장하지 않는다.

작업 폴더 `media/yt-edit/<job_id>/`에 `recipes.json`, `recipes.md`, `recipes.zip`을 저장한다. ZIP에는 전체 요약과 `01-recipe.json`, `01-recipe.md`, `02-recipe...` 형식의 메뉴별 파일이 들어간다. 완료 화면의 **레시피 요약 저장 / 인덱스 JSON 저장 / 메뉴별 파일 ZIP 저장** 버튼으로 인증 후 다운로드할 수 있다. 원본 기준 요약이므로 편집 영상에서 제외한 단계도 남으며, 표시 시간은 편집본 시간이 아니다. 이 기능은 레시피 문서 분리이며 메뉴별 MP4를 별도로 렌더링하는 기능은 아니다. 새 요약을 얻으려면 요리 카테고리로 다시 분석해야 한다. 다른 카테고리에는 추가 레시피 LLM 호출을 하지 않는다.

### 예능·게임 숏폼

판별 기준 **예능**(`variety`)을 추가했다. 예능과 **게임**(`game`)은 `app/services/edit_policy.py`의 별도 정책을 사용한다. 기본 목표는 120초이며 UI·API 목표 길이는 60~180초로 제한한다. 나머지 카테고리의 길이·가중치 정책은 변경하지 않는다. 숏폼 가중치는 히트맵 55%, 섹션 LLM 20%, 챕터 LLM 10%, 채팅·댓글·음량 각각 5%다. 히트맵이 없으면 가능한 나머지 점수로 재정규화한다.

`prompts/user/variety.json`, `prompts/user/game.json`은 재미·플레이의 중요도와 도입→핵심→반응·결말 보존을 지시한다. `prompts/system/short_form_context.json`은 관계 판별 시 추가 적용한다. 후보는 히트맵 중심 종합 점수순으로 검토하고, 앞뒤 90초의 주변 섹션(인접 챕터 포함)에서 LLM이 필수 맥락을 찾는다. 2초 이내로 이어지는 바로 앞뒤 섹션도 포함하고 첫 연결부터 마지막 연결까지 중간 섹션을 빠짐없이 선택한다. 중복 구간은 한 번만 포함하고 결과는 원본 시간순으로 정렬한다.

장면 묶음 추가 후 총길이가 목표 이상이면 종료하되 180초를 넘는 묶음은 쪼개지 않고 건너뛴다. 따라서 120초 목표가 문맥 보존 때문에 더 길어질 수 있으나 자동 선택은 180초 이내다. 원본이 짧거나 적합한 묶음이 부족하면 60초 미만일 수도 있으며 길이를 맞추려고 내용을 생성하거나 반복하지 않는다. 수동 선택도 렌더링 시 180초 초과를 거부한다. 이는 **길이만 숏폼**인 편집이며 세로 9:16 크롭·화면 추적·쇼츠 업로드는 추가하지 않았다. 기존 결과는 자동 변경되지 않으므로 앱을 재시작하고 해당 판별 기준으로 다시 분석한다.

`prompts/user/cooking_food.json`의 **요리·음식** 기준은 재료 설명 → 재료 손질 과정 → 조리 과정 → 완성된 음식 결과를 전달하는 섹션에 우선순위를 둔다. 방법·분량·불 세기·시간·완성 상태 등 필수 맥락을 보존하고 반복 동작·대기·잡담은 낮게 평가한다. 원본에 없는 단계는 만들지 않으며, 스크립트만으로 실제 완성 음식 화면의 존재를 확인하지는 않는다. 이는 LLM 중요도 평가 기준으로, 최종 선택은 종합 점수·문맥 연결·목표 길이의 영향을 받으므로 네 단계의 강제 포함이나 재배열을 보장하는 규칙은 아니다. 화면에서 해당 기준을 선택하고 중요도 평가부터 다시 실행해야 기존 결과에 반영된다.

`prompts/user/*.json`은 4-1의 판별 기준 드롭다운과 추가·수정·삭제 창에서 관리한다. 기본 제공 기준은 AI 뉴스(`ai_news`), 요리·음식(`cooking_food`), 교육·강의(`education_course`), 게임(`game`), 음악·공연(`music_performance`), 주식·증시(`stock`), 예능(`variety`) 7개이며 나머지 기본 카테고리 파일은 제거했다. 목록은 파일에서 동적으로 읽으므로 사용자 기준 추가·수정·삭제 기능은 유지된다. 각 파일은 `name`, `description`, `criteria` 문자열 키를 가진다. 모든 LLM 시스템 프롬프트는 `prompts/system/*.json`, JSON 응답 계약은 `prompts/schemas/*.json`에 저장하며 호출 시 파일을 읽는다. 시스템 프롬프트와 스키마는 별도 편집 UI를 제공하지 않는다.

기본 판별 기준은 AI 뉴스·주식·게임뿐 아니라 뉴스·시사, 스포츠, 음악·공연, 교육, 팟캐스트·인터뷰, 쇼핑·제품, 패션·뷰티, 영화·엔터테인먼트, 브이로그·IRL, 컨퍼런스, 과학·기술, 요리, 창작, ASMR, 종교·영성, 커뮤니티 토크, 건강·피트니스, 동물, 자동차, 비즈니스와 혼합 장르를 포함한다. 점수 판별은 장르 기준 적용, 섹션 역할 분류, 제거 가정에 의한 가치 판단, 챕터 내 상대 순위, 점수 분포 재교정 순서로 수행한다.

## 실행

의존성을 설치한 뒤 실행한다.

```powershell
python -m pip install -r requirements.txt
python -m app
```

`python -m app`은 로컬 FastAPI 서버를 백그라운드에서 실행하고 시스템 트레이 아이콘과 기본 React UI를 연다. 트레이에서 종료를 선택하면 진행 중인 작업 취소 여부를 확인하며, 확인 시 로컬 서버·AVE Server·RunPod에 순서대로 취소를 요청한 뒤 종료한다.

사용자 배포는 pynsist 설치 프로그램이 아닌 PyInstaller 기반 Windows x64 포터블 앱을 사용한다. 패키징 설정과 산출물은 형제 저장소 `ave-dist`에서 관리하며, 클라이언트 실행 파일·외부 정적 UI·FFmpeg/FFprobe 및 yt-dlp 업데이터를 포함한 ZIP을 생성한다. 이 저장소의 개발 실행과 기능 검증은 계속 `python -m app`을 기준으로 한다.

개발 중 UI를 수정했다면 다음 명령으로 빌드한다.

```powershell
cd ui
npm install
npm run build
```

WSL 1에서는 Windows Node.js 설치 경로를 확인할 수 없어 `npm run build`가 실행되지 않는다. 이 경우 Windows PowerShell에서 워크스페이스를 연 뒤 아래 명령으로 Python 테스트와 UI 빌드를 실행한다.

```powershell
cd modules\ave-client
.\.venv\Scripts\python.exe -m pytest -q
cd ui
npm run build
```

## LLM 요청 형식과 재시도

모든 편집 에이전트는 `공통 응답 계약 → 작업 지침 → 출력 스키마` 순서의 시스템 프롬프트를 사용한다. 공통 규칙은 `prompts/system/json_contract.json`, 단계별 지침은 기존 `prompts/system/*.json`, 데이터 타입은 `prompts/schemas/*.json`에서 관리한다. 주제별 `prompts/user/*.json`은 편집 판단 기준이며 JSON 형식을 바꾸지 않는다. 작업 입력은 별도 사용자 메시지로 전달한다. 점수 배치는 최대 32개이며 단일 섹션의 원문은 잘라내지 않아 매우 긴 섹션 하나는 입력 길이 예산을 넘을 수 있다.

JSON 형식·필수 항목·ID 계약 오류는 최대 3회, 타임아웃·연결 오류 및 일시적인 HTTP 408/429/500/502/503/504는 최대 4회 실패까지 시도한다. 통신 재시도에는 지수 대기와 짧은 무작위 지연을 적용하고 서버의 `Retry-After`를 존중한다. 요구 대기 시간이 60초를 넘으면 조기 재요청하지 않고 재시도 안내를 표시한다. 인증 오류·명확한 일일 한도 초과·키 설정 오류는 자동 반복하지 않는다. 서버가 오류 원인을 숨겨 전달하면 클라이언트는 해당 원인을 확정할 수 없다.

정상 검증된 응답만 공급자·모델·프롬프트·입력·스키마 기준의 체크포인트에 저장한다. 변경된 프롬프트는 처음 한 번 다시 분석한다. 완전한 JSON 코드펜스는 벗길 수 있지만 잘린 JSON·중복 키·NaN 등은 보정하지 않으며 임의 점수로 성공 처리하지 않는다. 프롬프트를 정형화해도 외부 서버 장애나 API 사용량 한도를 없앨 수는 없다.

## 구두점·의미 기준 문장 섹션

챕터 분할 요청은 `app/services/llm_analysis_service.py`의 `structure_transcript`에서 이번 입력의 첫·마지막 문장 ID와 문장 수를 프롬프트 및 `prompts/schemas/chapter.json` 기반 동적 스키마에 설정한다. `start_id`·`end_id`는 시간(초)이 아닌 정수 문장 ID이며 양끝을 포함한다. `_validated_ranges`는 타입·범위·역순·빈틈·겹침·마지막 ID 누락을 검증하고, 거부된 항목과 허용 범위를 다음 재시도에 전달한다. 3회 검증 실패 시 마지막 구체적 원인을 표시하며 잘못된 ID를 임의로 보정하지 않는다. 스키마와 프롬프트는 응답 캐시 키에 포함되므로 이전 계약의 캐시와 구분된다. 외부 API 오류나 LLM의 잘못된 응답 자체가 완전히 사라지는 것은 아니다.

요약 후보 선정에는 5초 최소 길이 제한을 적용하지 않는다. 5초 미만 문장도 고득점 핵심 구간과 필수 문맥 연결 후보에 모두 포함하며, 길이가 0 이하이거나 유한하지 않은 잘못된 구간만 제외한다. 점수순 핵심 구간 선정·LLM 필수 문맥 연결·목표 길이 종료 조건은 유지하므로 후보 포함이 최종 선택을 보장하지는 않는다. 기존 결과는 클라이언트 재시작 후 AI 추천 선택을 다시 실행해야 갱신된다.

3단계 분석 전에 `app/services/sentence_boundaries.py`가 원본 자막을 시간순으로 이어 읽고 마침표(`.`, `。`), 물음표, 느낌표에서 문장을 분리한다. `GPT 5.6`, `1.2.3`처럼 숫자 사이의 점은 제외하고, 구두점 뒤 공백이 없어도 분리한다. `네.`도 하나의 문장으로 보존한다. 기존 자막 ID나 줄바꿈에서는 문장이 끝나지 않으며, 마지막 구두점 없는 잔여 발화도 버리지 않는다. 이전의 연결 어미 기반 강제 병합은 더 이상 사용하지 않는다.

구두점으로 끝나지 않는 구간 또는 구두점 사이 120자를 초과하는 긴 구간은 `prompts/system/sentence_boundary.json`과 `LLMAnalysisService.split_unpunctuated_sentences`로 의미 기반 분할을 보완한다. 공백으로 구분되는 단어가 둘 이상일 때 적용하며 모든 카테고리에서 동일하게 동작한다. 120자는 LLM 검토 여부의 기준이지 문장 절단 길이가 아니다. 문법적으로 완결된 진술·질문·명령마다 나누고 연결 어미·인용문 내부에서는 자르지 않도록 지시한다. LLM은 문장 끝 단어 ID만 반환하며 원문이나 시간을 다시 쓰지 않는다. 원문에 공백도 없다면 단어 내부를 임의로 나누지 않는다.

긴 입력은 최대 240단어 창으로 요청하고, 창 끝의 미완성 문장은 다음 요청에 이어 보낸다. 경계를 전혀 찾지 못하면 480·960단어까지 문맥을 확대하며, 그래도 비최종 창의 경계가 없으면 임의로 자르지 않고 분석을 일시 중단한다. 단어 ID 범위·순서·누락은 검증하지만 LLM의 언어적 판단 정확성까지 보장하지는 않는다. 기존 API 재시도·취소·검증된 응답 캐시를 사용한다. 구두점이 부족한 입력에는 추가 LLM 요청과 사용량이 발생한다.

한 문장이 한 섹션이다. 전처리에서 위 문장 경계를 확정한 뒤 LLM은 상위 챕터 구성·중요도 평가·편집 판단을 수행하며 문장 섹션을 다시 병합하지 않는다. 2단계 Whisper 자막 준비의 LLM 분할은 별도 처리이며 유지한다. 기존 `prompts/system/section.json`은 3단계에서 호출하지 않는다. `analysis-transcript.json`과 편집 계획의 `script_segments`에는 새 문장 ID, 원본 ID 목록, 시작·끝 시간, `timing_estimated`가 저장된다.

단어 시간이 원문과 일치하면 단어 사이의 시간 중간점을 사용한다. 단어 시간 없이 자막 구간 내부를 나눠야 하거나, 단어 하나 안에 여러 문장이 있으면 문자 비율로 시간을 추정하고 섹션 카드에 **시간 추정 · 미리보기 확인 필요**를 표시한다. 이 값은 정확한 음성 정렬이 아니므로 미리보기로 싱크를 확인해야 한다. 추정 문장은 잘못된 단어 컷을 막기 위해 추임새 자동 제거 대상에서 제외한다. 원본 텍스트의 오타·띄어쓰기를 고치거나 내용을 삭제하지 않는다.

기존 표시 결과는 자동 변경되지 않는다. 클라이언트를 완전히 종료·재실행하고 구조 분석을 다시 수행한다. 문장 입력과 챕터 프롬프트가 변경되어 이전 LLM 체크포인트와 구분된다.

Gemini/DeepSeek 호출 오류에는 공급자 이름을 표시한다. 상세 코드가 없는 일반 502 응답이면 원격 `ave-server`의 업데이트·배포 상태와 로그를 확인한다. 이번 로컬 분할 변경은 원격 API 인증·한도 문제를 해결하지 않는다.

## AI 뉴스의 추임새 컷 편집

판별 기준 `ai_news`를 선택하면 렌더링 직전에 `prompts/system/filler_detection.json`으로 짧은 추임새의 문맥을 판별한다. 긴 방송 전체가 아닌 최종 선택한 영상 범위의 후보만 48개씩 LLM에 보내며 새 구간을 선택하면 해당 범위로 다시 판별한다. `네·녜·넵·어·음·아·뭐` 중 실제 단어 시간(WhisperX) 또는 YouTube VTT 인라인 시각으로 확인된 후보만 사용한다. 질문에 대한 답변·의미 있는 동의는 보존하도록 지시하며 LLM은 후보 ID만 반환한다. 추임새만 있는 짧은 자막은 자막 구간 전체를 후보로 사용할 수 있다. 단어 시각이 없는 문장 내부는 추정해서 자르지 않으며 진행 메시지에 전체 스크립트의 해당 구간 수를 표시한다.

확정된 구간은 실제 영상·오디오에서 잘라내고, 동일한 제거 시간을 반영해 자막 시간축을 재계산한다. 짧은 컷은 오디오 샘플 단위 trim과 영상 시각 보정으로 렌더링한다. 개별 후보는 0.04~1.2초로 제한하며, 선택한 영상에서 제거 시간이 20%를 넘으면 해당 렌더링에서는 추임새 제거를 생략한다. 원본 영상과 분석 섹션은 변경하지 않으므로 섹션 미리보기에는 원래 발화가 보이고 최종 렌더링에 제거가 적용된다. 새 구간을 선택해도 원본 기준으로 다시 계산한다.

제거 후보와 결과는 작업 폴더의 `*.analysis-plan.json` 안 `filler_cuts`, `filler_missing_timing`, `filler_summary`에 기록한다. 최초 판별에는 추가 LLM 요청이 들며 동일 요청의 재시도는 기존 체크포인트를 사용한다. 적용하려면 클라이언트를 재시작하고 2단계 자막 자료 준비(Whisper는 전사 준비)부터 새 분석을 진행한다. 기존에 생성된 편집본은 자동 변경되지 않는다.

## 주요 API

* `POST /api/youtube/metadata`: 영상 메타데이터 조회
* `POST /api/youtube/metadata/materials/start`, `GET /api/youtube/metadata/materials/{job_id}`: 2단계 자료 준비와 일회성 완료 응답 조회
* `POST /api/youtube/edit/start`: 분석 작업 시작
* `GET /api/youtube/edit/{job_id}/events`: 분석·렌더링 진행 상태 SSE 스트림
* `GET /api/youtube/edit/status/{job_id}`: SSE 재연결 전 상태 확인
* `GET /api/youtube/edit/active`, `POST /api/youtube/edit/{job_id}/cancel`: 진행 작업 복구와 단일 작업 취소
* `POST /api/youtube/edit/cancel-active`: 브라우저 확인 또는 트레이 종료 시 모든 활성 작업 취소
* `GET`/`PUT /api/youtube/edit/{job_id}/segments`: 추천 구간 조회·선택 렌더링
* `GET /api/youtube/edit/{job_id}/media/source`: 활성 선택·렌더링 작업의 원본 미리보기
* `GET /api/youtube/edit/{job_id}/media/rendered`: 완료된 결과 영상 조회
